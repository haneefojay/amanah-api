# Architecture

How the Amanah API fits with the rest of the system. Decisions behind it are in [`decisions/`](./decisions/README.md); requirements are in the [spec](./amanah-mvp-spec.md).

## Parts

| Part | Technology | Repository / host |
| ---- | ---------- | ----------------- |
| Frontend | Next.js 16 PWA | https://github.com/haneefojay/amanah, Vercel (ADR-008) |
| API | FastAPI, Pydantic v2 | this repository, Railway (ADR-012) |
| Database | PostgreSQL, SQLAlchemy 2, Alembic | Railway PostgreSQL |
| Files | MinIO (S3 API) | Railway service with a volume (ADR-013) |
| Payments | Paystack, test mode | external |

## Contract between frontend and backend

- JSON over HTTPS. Paths follow spec §8 (`/api/campaigns`, `/api/campaigns/:id/checkout`, `/api/webhooks/payments`, …).
- The **OpenAPI 3.1 document** generated by FastAPI is the source of truth (B0.3). It is exported to the repository and CI fails if it is stale. The frontend generates types from it and reconciles its Zod schemas and MSW handlers.
- Until each endpoint is integrated, the frontend runs against its mock API (ADR-003). The mock shapes are in the frontend's `src/lib/api/schemas.ts`; the real API should match them unless the user decides otherwise.
- Money is integer kobo. Timestamps are ISO 8601 UTC. Errors use `{ "error": { "code", "message" } }`. Lists are paginated with a single convention set in B0.3.

## Authentication and sessions (ADR-011)

1. `POST /api/auth/login` verifies the argon2id hash and creates a session row (token stored hashed).
2. The response sets an httpOnly, Secure, SameSite cookie. The browser never sees the token in JavaScript.
3. Every protected route depends on a guard that loads the session, checks the role and, for `/api/org/*` and `/api/witness/*`, the organisation membership or assignment.
4. State-changing requests carry CSRF protection.
5. Donors are guests and never have sessions (D7).

**Cross-origin note:** the frontend and API run on different hosts. For the cookie to work in all browsers they must share a registrable domain, or the frontend must proxy `/api/*` to the API. Decide this before staging.

## The donation cap (spec §4)

Checkout creates a **reservation** inside a transaction that locks the campaign row (`SELECT … FOR UPDATE`). `available = target − raised − active reservations`. The reservation ID is the Paystack reference. A verified, idempotent webhook locks the campaign and reservation again, creates the donation and moves the reservation to `CONFIRMED`. A scheduled job (or lazy check) expires reservations. A late payment past the target creates an `ExcessRecord` and alerts the platform admin. The concurrency suite (B6.3) is the acceptance test.

## Storage (ADR-013)

The API uses an S3-compatible adapter. `private` bucket: verification documents, served by short-lived signed URLs. `public` bucket: receipts, evidence and update photos. Upload time is set by the server and is authoritative (spec §7).

## Deployment (ADR-012)

Dockerfile, configuration only through environment variables (see `.env.example`), migrations on deploy, `GET /health` checks the database. Staging and production are separate environments. The same container runs on a VPS later with `docker compose`.

## Security baseline

Rules in the backend roadmap's non-negotiables: kobo integers, locked-transaction cap, double-verified webhooks, idempotency, append-only audit log, access control with organisation scoping, secrets in environment variables only, no donor contact data in public responses.
